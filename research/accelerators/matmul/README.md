# INT8 matmul accelerator research data

This folder holds small, committed summaries of measurements on the INT8 matmul accelerator RTL (Project 3), so that a change to the design shows up as a reviewable diff. Raw tool output does not belong here: full logs, netlists, waveforms, runner outputs and per-size builds stay in `hardware/accelerators/matmul/build/`, which is git-ignored and rebuilt by the make targets.

Every file here is written by a make target, never by hand, and records the git commit, the architecture revision, the array size and the tool versions it came from. Every number in it comes from a command that was actually run: cycle counts from the Verilator runner, resources from Yosys, Fmax estimates from nextpnr for a named FPGA. Simulator wall-clock time is never reported as hardware speed, and power is "not measured".

The Project 3 tickets add their reports here, and each documents its files in the table below when it does:

| Path                                      | Written by                                                | Contents                                                                                                                                                                                                                                        |
| ----------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `synth/`                                  | the synthesis ticket (`make synth`)                       | Generic, iCE40 and ECP5 resource and timing summaries of the 4 × 4, 8 × 8 and 16 × 16 arrays                                                                                                                                                    |
| `reports/<date>-<shortsha>.{json,csv,md}` | `make -C hardware/accelerators/matmul benchmark-baseline` | A benchmark report (schema below): transfer-in, compute, store, transfer-out and total cycles, MACs, PE utilisation and MACs and ops per cycle of every benchmark workload on the 4 × 4, 8 × 8 and 16 × 16 arrays, gated on the reference model |
| `experiments/<name>/`                     | the design-space ticket (`make experiment`)               | The configurations an experiment compares, and its results with the Pareto-optimal designs                                                                                                                                                      |
| `cpu-comparison/`                         | the CPU comparison ticket                                 | VCPU-8 against the accelerator on the same tiny INT8 matmul workloads                                                                                                                                                                           |

## What gets committed

Only small JSON, Markdown and CSV reports. Never commit raw logs, netlists, waveforms (`.vcd`, `.fst`), test vectors, runner outputs or build directories. Commit a report from a clean working tree, so its dirty flag is `false` and its commit identifies exactly the design it measured.

Every report is JSON with a zod schema and `schemaVersion: 1` (fields are only ever added; removing or redefining one bumps it), plus a Markdown rendering, and records `revision`, the git commit and dirty flag, the array size (`ROWS` × `COLS`) and the `build/tool-versions.json` provenance. A MAC is one multiply plus one accumulate, and reports count MACs.

## The architecture revision

`hardware/accelerators/matmul/REVISION` names the microarchitecture: `matmul-os-r1` (matmul, output-stationary, revision 1). Bump the number in the same commit as any change that is visible in cycles (a controller state added or removed, a different skew, a different buffer interface). A change that leaves every cycle count unchanged keeps the revision; the git commit tells those apart. A different dataflow (for example weight-stationary) gets a new prefix. The array size is a parameter, not a revision: reports record it separately. [docs/hardware/accelerators/architecture.md](../../../docs/hardware/accelerators/architecture.md) is the contract for `matmul-os-r1`.

## The benchmark report

`make -C hardware/accelerators/matmul benchmark` writes `build/reports/benchmark.{json,csv,md}`; `make benchmark-baseline` also writes the commit-ready copies `reports/<date>-<shortsha>.{json,csv,md}` and refuses to from a dirty working tree (`ALLOW_DIRTY=1` overrides it, for a report that is not to be committed). The JSON follows `BenchmarkReportSchema` in [packages/accelerator-reference/src/harness/report.ts](../../../packages/accelerator-reference/src/harness/report.ts), `schemaVersion` 1, `kind` `matmul-rtl-benchmark`. Fields are only ever added; removing or redefining one bumps `schemaVersion`. The CSV has a header row and one row per (array size, workload) with the same numbers; the Markdown has a cross-size summary and one table per array size. [docs/hardware/accelerators/performance-analysis.md](../../../docs/hardware/accelerators/performance-analysis.md) explains every column and what the numbers show.

| Field          | Contents                                                                                                                                                                                                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `revision`     | `hardware/accelerators/matmul/REVISION`                                                                                                                                                                                                                                                                                      |
| `arraySizes`   | The array sizes benchmarked, `<ROWS>x<COLS>`, smallest first                                                                                                                                                                                                                                                                 |
| `labels`       | What a MAC is (one multiply plus one accumulate; ops = 2 × MACs), what the cycles are (RTL clock edges, not time; no clock frequency assumed), what the transfer clocks are (the testbench host port) and how utilisation is defined                                                                                         |
| `formulas`     | The formula of every derived column, among them `utilization = macs / (ROWS · COLS · compute)`                                                                                                                                                                                                                               |
| `config`       | The workload notation (M × K × N), the seed and generator, the workloads and the correctness gate                                                                                                                                                                                                                            |
| `verification` | Whether the correctness gate passed, the case counts and the cases that failed it                                                                                                                                                                                                                                            |
| `rows`         | Per (array size, workload): the dimensions and, for a case that passed the gate, MACs, tiles, transfer-in, compute, store, busy, transfer-out and total cycles, fill/drain clocks, utilisation, MACs and ops per cycle (compute phase and whole run) and bytes in and out; for a case that failed, the reason and no numbers |
| `provenance`   | When (`createdAt`), the git commit (`gitCommit`, `gitShortCommit`) and dirty flag (`gitDirty`), the runner of each size, the toolchain and tool versions (from `build/tool-versions.json`)                                                                                                                                   |
| `host`         | Simulator wall-clock time per case, on this machine: it measures the simulator, not the accelerator                                                                                                                                                                                                                          |

Everything except `provenance` and `host` is modelled accelerator behaviour and is deterministic: two runs of the same design give byte-identical JSON once those two sections are removed, which `make benchmark-compare` checks against the newest committed `reports/*.json` (or `BASELINE=<file>`).
