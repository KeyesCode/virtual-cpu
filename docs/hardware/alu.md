# The VCPU-8 ALU

`hardware/rtl/vcpu8/core/vcpu8_alu.sv` is the arithmetic logic unit of the RTL CPU. It is purely combinational: it holds no state, has no clock, and its outputs depend only on its current inputs. It reproduces `packages/cpu-core/src/alu.ts` bit for bit, result and flags, for every operation and every operand. An exhaustive test proves this against vectors generated by running the TypeScript ALU itself.

The equations here are the same as the table in [hardware-porting.md](../hardware-porting.md#alu-alu) and the rules in [instruction-set.md](../instruction-set.md#exact-flag-rules). This document explains them and how each one becomes logic.

## Interface

| Port    | Dir | Width | Meaning                                                                |
| ------- | --- | ----- | ---------------------------------------------------------------------- |
| `a`     | in  | 8     | First operand: field a of the register byte (the destination register) |
| `b`     | in  | 8     | Second operand: field b. Unary operations ignore it                    |
| `op`    | in  | 4     | `vcpu8_types_pkg::alu_op_t`, selected by the decoder                   |
| `c_in`  | in  | 1     | The current C flag. Only INC and DEC read it                           |
| `div_q` | in  | 8     | The iterative divider's quotient. Read only when `DIV_ITER = 1`        |
| `r`     | out | 8     | Result                                                                 |
| `z`     | out | 1     | `r == 0`, for every operation                                          |
| `c`     | out | 1     | Carry, borrow or shifted-out bit; see the table                        |
| `n`     | out | 1     | `r[7]`, for every operation                                            |
| `v`     | out | 1     | Signed overflow; see the table                                         |

The parameter `DIV_ITER` (default 0) selects the divider. With 0, the v1 design, DIV is the combinational divider below and `div_q` is ignored. With 1, the ALU has no divider: `ALU_DIV` passes `div_q` through, the quotient of the [iterative divider](#iterative-divider), and Z, N, C and V are formed from it exactly as before. `vcpu8_core` sets it from its own `DIV_ITER`.

CMP has no `alu_op_t` value of its own. The decoder selects `ALU_SUB` for it and disables the register write, so CMP sets exactly the flags SUB would.

The ALU always produces all four flags. Which of them an instruction may change is the per-opcode FLAGS write mask, `isa_flag_mask` in the generated ISA package, which is applied outside the ALU:

```systemverilog
flags_next = (flags & ~flag_mask) | ({z, c, n, v} & flag_mask);
```

INC and DEC have the mask `1011`, so C keeps its old value. The ALU also passes `c_in` through on C for them, so its outputs alone already match `inc()` and `dec()` in TypeScript, which return the complete new FLAGS byte.

## Operations and flags

Z and N are computed the same way for every operation:

```systemverilog
assign z = (r == 8'h00);
assign n = r[7];
```

| `op`      | `r`                                          | C              | V                                     |
| --------- | -------------------------------------------- | -------------- | ------------------------------------- |
| `ALU_ADD` | `sum[7:0]`, `sum = {1'b0,a} + {1'b0,b}`      | `sum[8]`       | `(a[7] == b[7]) && (sum[7] != a[7])`  |
| `ALU_SUB` | `diff[7:0]`, `diff = {1'b0,a} - {1'b0,b}`    | `diff[8]`      | `(a[7] != b[7]) && (diff[7] != a[7])` |
| `ALU_MUL` | `prod[7:0]`, `prod = a × b` (16 bits)        | `\|prod[15:8]` | `\|prod[15:8]`                        |
| `ALU_DIV` | `a / b` (unsigned, floor); `0` when `b == 0` | `0`            | `0`                                   |
| `ALU_INC` | `a + 1`                                      | `c_in`         | `a == 8'h7F`                          |
| `ALU_DEC` | `a - 1`                                      | `c_in`         | `a == 8'h80`                          |
| `ALU_AND` | `a & b`                                      | `0`            | `0`                                   |
| `ALU_OR`  | `a \| b`                                     | `0`            | `0`                                   |
| `ALU_XOR` | `a ^ b`                                      | `0`            | `0`                                   |
| `ALU_NOT` | `~a`                                         | `0`            | `0`                                   |
| `ALU_SHL` | `{a[6:0], 1'b0}`                             | `a[7]`         | `0`                                   |
| `ALU_SHR` | `{1'b0, a[7:1]}`                             | `a[0]`         | `0` (and N is always 0)               |

The four unused `alu_op_t` codes (12 to 15) give `r = 0`, C = V = 0. The module is a single `always_comb` block that assigns `r`, `c` and `v` defaults before its `case`, so every path assigns every output and no latch can be inferred.

### C on subtraction is a borrow

`diff = {1'b0,a} - {1'b0,b}` is computed in 9 bits. When `a >= b` unsigned, the difference fits in 8 bits and `diff[8]` is 0. When `a < b`, the subtraction wraps modulo 512 and `diff[8]` is 1. Bit 8 is therefore exactly the **borrow**, and C holds it directly: `SUB 00, 01` gives `r = FF` with C = 1.

Some CPUs (the 6502, ARM) store the inverted value, "carry = not borrow", because they subtract by adding the complement and keep that adder's carry-out. VCPU-8 does not. JC after CMP jumps when the first operand is unsigned-less-than the second.

### Signed overflow

V is set when the 8-bit result read as a two's-complement number is not the true signed result.

- **ADD.** Adding two numbers of opposite sign can never overflow, because the sum lies between them. Adding two numbers of the same sign overflows exactly when the result has the other sign: two positives give a "negative", or two negatives give a "positive". Hence `V = (a[7] == b[7]) && (r[7] != a[7])`. Example: `7F + 01 = 80`, that is +127 + 1 reading as −128, so V = 1.
- **SUB.** `a − b` is `a + (−b)`, so the operand signs that can overflow are the opposite ones. Overflow happens when they differ and the result's sign differs from `a`: `V = (a[7] != b[7]) && (r[7] != a[7])`. Example: `80 − 01 = 7F`, that is −128 − 1 reading as +127, so V = 1.
- **INC and DEC** are ADD and SUB with a constant 1, and the rules reduce to a single input value each: only `7F + 1` and `80 − 1` overflow.
- **MUL** sets V to the same value as C: the unsigned product did not fit in 8 bits. The ISA defines it this way. It is not a signed-overflow test.

## How each operation becomes logic

The RTL is written as arithmetic (`+`, `-`, `*`, `/`) and lets synthesis choose the circuits. This is what they are.

- **ADD** is a 9-bit adder. The textbook form is a ripple-carry adder: eight full adders in a chain, each producing a sum bit `a ^ b ^ cin` and a carry `(a & b) | (cin & (a ^ b))`, with C taken from the last carry. Yosys maps `$add` to its own adder structure. On an FPGA, `synth_ice40` uses the dedicated carry chain.
- **SUB** reuses the same idea: `a − b = a + ~b + 1`. That is the adder with `b` inverted and a carry-in of 1. The 9-bit form above keeps the borrow convention without inverting the carry-out.
- **INC and DEC** are the same adder with a constant operand. Their V is an 8-input equality comparator.
- **MUL** is an 8 × 8 array multiplier. Each of the 64 partial-product bits is one AND gate `a[i] & b[j]`, and rows of adders sum the shifted partial products into 16 bits. C = V is an 8-input OR of the high byte.
- **DIV** is an array divider: eight restoring-division stages, each a subtract-and-compare followed by a multiplexer that keeps either the difference or the old remainder. Each stage waits for the one before it, so the circuit is deep.
- **AND, OR, XOR and NOT** are one gate per bit.
- **SHL and SHR** use no gates at all. A constant shift is wiring: output bit `i` is input bit `i ∓ 1`, the vacated bit is tied to 0, and the bit shifted out becomes C.
- **Z** is an 8-input NOR of `r`. **N** is the wire `r[7]`.
- **Selecting an operation** is a 12-way multiplexer on `op` in front of `r`, `c` and `v`. Every operation's circuit is present in parallel, and the multiplexer passes one of them through.

### MUL and DIV are combinational in v1

This follows the brief's rule of using the simplest correct synthesizable implementation first. The whole product and the whole quotient settle within one EXECUTE cycle, so they cost no extra cycles, but they are the largest and deepest logic in the ALU. Yosys 0.70+145 from the pinned OSS CAD Suite reports the following for the ALU and for each block synthesized alone (`synth -flatten`, then `abc -g AND,NAND,OR,NOR,XOR,XNOR,ANDNOT,ORNOT,MUX` to count simple gates):

| Block                                 | Gates | Longest path (`ltp -noff`) |
| ------------------------------------- | ----- | -------------------------- |
| `vcpu8_alu` (all operations)          | 778   | 74                         |
| 8 × 8 → 16 multiplier                 | 326   | 29                         |
| 8 ÷ 8 divider with the `b == 0` guard | 214   | 71                         |
| 9-bit adder                           | 38    | 15                         |

The divider is smaller than the multiplier but more than twice as deep, and it alone sets the ALU's longest path, and so the clock period the ALU allows. A restoring divider that produces one quotient bit per clock removes that depth at the cost of extra EXECUTE cycles per DIV ([hardware-porting.md](../hardware-porting.md#alu-alu) sketches one iteration per quotient bit). [The iterative divider](#iterative-divider) below is that alternative, and the [div-impl experiment](../../research/cpu/experiments/div-impl/README.md) measures the trade-off. It changes cycle counts, never results.

These numbers come from generic gates and are only indicative. The synthesis ticket reports the real FPGA resource and timing figures. To reproduce them:

```sh
yosys -p 'read_verilog -sv hardware/rtl/vcpu8/core/vcpu8_types_pkg.sv hardware/rtl/vcpu8/core/vcpu8_alu.sv;
          synth -top vcpu8_alu -flatten; abc -g AND,NAND,OR,NOR,XOR,XNOR,ANDNOT,ORNOT,MUX;
          opt_clean; stat; ltp -noff'
```

### Divide by zero

DIV with `b = 0` is a fault. The control unit checks `b == 0` before any state is written and raises `DIVIDE_BY_ZERO`, so the ALU's output for it is never used. The check does not depend on the divider.

The ALU still has to produce something defined for `b = 0`, because simulation, formal tools and synthesis all see that input. In plain Verilog, `a / 0` is X. The `b == 8'h00` guard therefore forces the quotient to 0, giving `r = 00`, Z = 1, C = N = V = 0. No X can reach the datapath, and the guard costs a few gates.

## Iterative divider

`hardware/rtl/vcpu8/core/vcpu8_divider.sv` is the alternative to the combinational divider: an unsigned 8-bit restoring divider that finds one quotient bit per clock. It is used only when the design is built with `DIV_ITER = 1` (`make … DIV_IMPL=ITER`, or the `div-iter` variant of the experiment); the default build does not instantiate it.

| Port    | Dir | Width | Meaning                                                                           |
| ------- | --- | ----- | --------------------------------------------------------------------------------- |
| `start` | in  | 1     | Begin a division of `a` by `b`. Sampled only when idle (`busy` low)               |
| `a`     | in  | 8     | Dividend; read only in the start cycle                                            |
| `b`     | in  | 8     | Divisor, non-zero; latched in the start cycle                                     |
| `busy`  | out | 1     | High for the 7 cycles after the start cycle                                       |
| `done`  | out | 1     | One-cycle pulse, exactly 8 cycles after the start cycle                           |
| `q`     | out | 8     | Quotient `a / b`, valid from the `done` cycle until the next start                |
| `rem`   | out | 8     | Remainder `a % b`, likewise. Only the unit test reads it; the core leaves it open |

Each iteration shifts the next dividend bit into the partial remainder and subtracts `b` if it fits:

```text
t = {rem, q[7]}                      // the dividend shifts out of q from the top
if (t >= b)  rem = t - b, q = {q[6:0], 1}
else         rem = t,     q = {q[6:0], 0}
```

`rem < b` holds after every step, so `t` fits in 9 bits and `t - b` in 8. The datapath is one 9-bit subtractor, a 16-bit shift register for the remainder and quotient, the latched divisor and a 3-bit step counter. The start edge itself performs the first iteration from `a` and `b`, so the eight iterations end at the eighth edge and `done` comes 8 cycles after the start cycle. `rst` returns the divider to idle from any state. A start while `busy` is ignored. The CPU never starts it with `b = 0`, because `DIVIDE_BY_ZERO` is raised first ([Divide by zero](#divide-by-zero)), but the outputs are still defined then: every step subtracts nothing, giving `q = FF` and `rem = a`.

In the core, the divider reads the same operands as the ALU, and the control FSM holds DIV in EXECUTE until `done` ([control-unit.md](control-unit.md#states)). The quotient stays in `q` through WRITEBACK, where the ALU passes it on as DIV's result through `div_q`. DIV therefore takes 13 clocks instead of 5, and its result and flags are unchanged.

`make -C hardware/rtl/vcpu8 test-divider` (part of `make test`) checks the module on its own. `pnpm --filter @vcpu/rtl-tools gen:div-vectors` (`packages/rtl-tools/src/gen/div-vectors.ts`) calls `div()` from `@vcpu/cpu-core` for every `(a, b ≠ 0)` and writes 65,280 records of `{a, b, q}` to `build/vectors/div.hex`. `tb/unit/tb_vcpu8_divider.sv` runs each one through a full handshake: one start pulse, then different values on `a` and `b`, so the divider must use what it latched. It requires the expected `q`, `q × b + rem = a` with `rem < b`, `busy` high and `done` low until `done` arrives exactly 8 cycles after the start cycle, and `done` low again in the next cycle. Directed checks follow: a start while busy is ignored, `rst` while busy returns to idle with no `done`, and `b = 0` gives X-free outputs. The run on this commit prints:

```text
divider: 65280 vectors, 0 mismatches, done 8 cycles after start; 3 directed checks, 0 failed
```

The vitest test `packages/rtl-tools/src/gen/div-vectors.test.ts` checks the record count, the format and the edge cases (`0 / x = 0`, `FF / 1 = FF`, `x / x = 1`) against the reference, without the hardware toolchain.

## Verification

The proof is an exhaustive comparison with the TypeScript ALU. Its expected values are never derived by hand.

1. `pnpm --filter @vcpu/rtl-tools gen:alu-vectors` (`packages/rtl-tools/src/gen/alu-vectors.ts`) calls `ALU_OPERATIONS` from `@vcpu/cpu-core` for every input below and writes `hardware/rtl/vcpu8/build/vectors/alu.hex`, plus `alu.meta` with the record count. The op codes are read from `alu_op_t` in `vcpu8_types_pkg.sv`, so the vectors and the RTL cannot disagree about them.

   | Operations                       | Inputs                                     | Records     |
   | -------------------------------- | ------------------------------------------ | ----------- |
   | ADD, SUB, CMP, MUL, AND, OR, XOR | all 256 × 256 `(a, b)`                     | 7 × 65,536  |
   | DIV                              | all `(a, b)` with `b ≠ 0`                  | 65,280      |
   | INC, DEC                         | all 256 `a` × all 16 incoming FLAGS values | 2 × 4,096   |
   | NOT, SHL, SHR                    | all 256 `a`                                | 3 × 256     |
   | **Total**                        |                                            | **532,992** |

   Each record is one 36-bit `$readmemh` word, `{op[3:0], a, b, flags_in[3:0], r, flags[3:0]}`, with flags in ZCNV order (FLAGS bits 3 to 0). CMP records use op code `F` and drive `ALU_SUB`.

2. `tb/unit/tb_vcpu8_alu.sv` loads the records, drives each one into `vcpu8_alu` and compares `r` and ZCNV. Before the comparison it fails if `alu.hex` holds fewer or more records than `alu.meta`. It then:
   - repeats nine documented edge cases by name (ADD `7F+01` and `FF+01`, SUB `00−01` and `80−01`, CMP `05−05`, MUL `10×10`, INC `FF` and DEC `00` with C set, SHR `01`), looking up their expected values in the vectors;
   - sweeps DIV over all 256 values of `a` with `b = 0` and checks that no output is X or Z. Verilator simulates two-state logic, so this check cannot itself see an X. The X-freedom comes from the explicit guard above, and the formal ticket can prove it.
   - prints the totals and the first 20 mismatches, and exits non-zero through `$fatal` if any check failed.

3. `test-alu` then runs `test-alu-corrupt`. It copies the vectors, flips the expected flags of one record (SUB `00 − 01`, vector 65,537), and requires the testbench to exit non-zero with a `MISMATCH vector 65537` line. This shows the harness can fail.

Run it with:

```sh
make -C hardware/rtl/vcpu8 test-alu      # or `test` for every unit test
```

The vectors are regenerated when the generator, the CLI, `alu.ts` or `vcpu8_types_pkg.sv` changes. To run the testbench on other vectors, pass `+vectors=<file>`; it reads the record count from the `.meta` file beside it, or from `+meta=<file>`. On an Apple Silicon Mac, Verilator simulates the full sweep in about one second, so the vectors stay in a single file.

The vitest test `packages/rtl-tools/src/gen/alu-vectors.test.ts` runs in `pnpm test` without the hardware toolchain. It checks the record count per operation, the record format, the op codes against `alu_op_t`, and the documented edge cases against the reference.
